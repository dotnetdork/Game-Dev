# V2 review, round 2: critique, V1 vs V2, and the plan

**Status: draft for Jay, 2026-09-28.** Nothing here is approved, and no code has changed. It comes from
Jay's first real playthrough of the V2 studio and the interview (screenshots, 28 Sept), from six
read-only reviews run in parallel, and from my own reading of every line cited as a root cause. Once
Jay answers the open questions (§8), it becomes a spec amendment to `v2-spec.md`, and building starts
from that (see memory: spec before building).

---

## 1. What we found, in one paragraph

The V2 shell is the right idea. The engine layout, panels arriving in story order, beats that wait
on evidence, tickets that are never lost, and the Play-mode revert all work, and the tests pass
(19/19). But **nothing Jay saw in the studio came from an AI.** Every line was either verbatim YAML
or a string hard-coded in `quest.js`. The Director, Builder, Art scout and Checker are not built.
The hero picker is a regex. The only live AI call in the studio is a typed line to one mentor
prompt that wears different names. So the studio reads as a script with a chat skin: it gives the
answers away, loops, merges every speaker into one stream, and runs out of content about 45 minutes
into a 2-hour session. At that point the chat also freezes. The interview does call the AI on every
turn (it runs on Claude Sonnet 5 locally, via `TUTOR_MODEL`). But its goals are satisfied by *facts*
("plays RuneScape") rather than *reasons*, so it moves on before it has learned anything.

## 3. V1 vs V2: what to carry over

| Area | V1 (`main`) | V2 (this branch) | Take from V1 |
|---|---|---|---|
| AI building | Coder → JSON ops → 4 guards + retry → config applies at once, code as a reviewed diff (`main:app/routes/ai.js:328-556`, `main:app/public/js/ops.js`) | the mentor can only flip whitelisted values (`quest.js:318-330`); no Builder | **the whole pipeline, as the Builder**: ops, `validJS`, `keepsTopLevelFunctions`, the guard table (no-ops, bad-api, bad-key, bad-asset) |
| Agent tools | `search_phaser_docs`, `read_file`, `search_store`, `list_owned_assets` (`main:app/ai/tools.js`) | off for the mentor (right for chat) | back on for the Builder and the Art scout |
| Errors | honest, status-specific messages (401/429/5xx, `main:app/public/js/ai.js:743-752`) | every failure becomes "pinned to your idea board" | the honest messages |
| Saves | migrations; unreadable saves set aside, never overwritten | a version change wipes the game (`project.js:33-37`) | migrate-or-set-aside |
| Orientation | 11 destinations, no tour, practice steps on another tab | panels in story order, evidence-driven beats | V2 wins; keep V1's ledger rule (never redo finished work) |
| Code | Code tab plus explain-a-line (`main:app/ai/skills/explain-a-line.md`) | no Script panel yet (`reveal: [script]` silently does nothing) | explain-a-line in the Script panel, voiced by the current character |
| Design | Design board + coach, which *does* write stickies via checked `BOARD:` ops | none | a **Design Doc** asset in Project, which the Design department opens |
| Rewards | badges earned only by doing it in your own game | concept cards | the rule, not the badges |
| Showing off | Gallery/Leaderboards were empty placeholders | none | nothing; build a class **Showcase** wall at Launch instead (no ranking) |
| Chat feel | every turn a model call, with tools: slow and unpredictable; the first helper refused to build | authored lines are instant; one tool-free call per typed line | V2's shape, plus V1's rotating status text (already copied) |

**The lesson from the comparison:** V2 is snappy and predictable *because it can't do anything*.
Once the Builder lands, V1's latency and failure modes come back. So keep chat tool-free and fast,
and run building as its own call with a visible working state and V1's guards.

## 4. The AI: how it should work

### Options

| | How it works | Per-turn cost | Predictability | Fails how |
|---|---|---|---|---|
| **A. Script + AI voicing** | beats as today; the AI rewrites each line | 1 call per beat (prefetchable) | high | keeps every structural bug; still feels canned |
| **B. Straight chat** | the AI drives; code only checks evidence | 1 call per turn, taps included | low | skips goals, gives answers anyway, rambles; dead when the AI is down |
| **C. Chat-first, code-owned goals** *(recommended)* | the quest defines **goals, evidence and hint levels**; the conversation is free chat; the AI chooses wording and order inside the current goal; cards appear only for a real choice | 1 call per kid turn; evidence-driven lines can play instantly | high where it matters (progress, awards, what counts as done) | nags or reveals, which the rules below prevent; with no AI, today's script runs |

C is Jay's "straight chat, as long as it's snappy and predictable". The chat *feels* free, while the
parts that must be predictable (what's done, what's awarded, what's changed) stay in code. The
interview already works this way (`interview.js:8-23`). **Latency is unmeasured:** time real
Sonnet 5 round-trips on the studio's context before Sunday, and consider streaming the reply, which
V2 doesn't do today.

### Rules (prompt + engine)

1. **Never narrate what the kid hasn't noticed.** The game logs events; only the kid *reports*
   them. Reactions to events are questions ("Hear anything?"), never conclusions. Only tickets the
   kid actually found get filed.
2. **Try first, then a hint ladder.** Each goal carries `hints: [where, which, how]`. Code holds the
   level and raises it on a timer or a failed try; the AI words it. The fix itself is never stated
   before hint 3, and at hint 3 the character offers to do it *together*: "tap it with me".
3. **"Why?" branches, then moves on.** A new `goto: resume` answers and then goes to the next beat.
   A repeat card never shows an option that has already been picked.
4. **One idea per bubble, at most ~25 words.** No merging across beats, and nothing merged while the
   game runs (hold lines until Stop). The validator warns on `say` lines over 20 words.
5. **Cards only for real choices.** No "Ready?", "Make sense?" or one-answer cards: those are Next
   buttons in disguise. Naming the game, describing a hero and asking why are all chat.
6. **Each character is a real character.** A voice sheet per character (`ai/skills/voice-*.md`): role,
   what they care about, three phrases, what they never say. Their own chat tab, colour and icon. A
   visible hand-off ("Sound designer joined") and hand-back.
7. **Wrong answers retry;** they never advance like right ones.
8. **The Director runs at quest end.** One call returns the next suggested ticket and a one-line
   bridge that recaps the card just earned, from a character with a reason to ask ("The sound
   designer loved that ding. Engineering has one for you…"). There is a static fallback. A clear
   board goes to own-game time, never to a dead end.
9. **A request the studio can't do yet** goes on a visible Ideas list, never into a promise.
10. **A 12 s client timeout**, then the scripted line. After two failures, stay scripted for the
    session and show it quietly in the status bar.

## 5. The interview: make it listen

**Why it's generic:** the goals are facts. `games` is done once a game is named. The clipboard
records "plays RuneScape, Project Zomboid", which is useless to a studio. The context then pushes
the model toward the next tablet test.

**Redesign: a player profile built by laddering** (what → which part → why → compared with what).

- **The goal is an element plus a reason, not a game.** For each game the kid loves, the interview
  needs one *element* and one *why*, and where it can, a *contrast*:
  - *RuneScape* → "which part: the skills, the quests, the world, the people?" → "the grind" →
    "what makes grinding fun there?" → "you can see your level go up" → "WoW has levels too; why
    RuneScape?" → "you can do any skill, in any order".
  - Recorded as **progression: visible, self-paced; freedom of order**.
- **The element taxonomy** (the studio's own words, for the clipboard):
  - movement and feel;
  - combat or challenge;
  - puzzles;
  - exploring and secrets;
  - building or making;
  - collecting;
  - progression or the grind;
  - story and lore;
  - characters;
  - humour and chaos;
  - calm and cozy;
  - friends (co-op, competing, trading).
- **Code decides when a goal is done:** only once `learned` has `{game, element, why}`. The model
  must dig at least twice on the first game before moving on, and it's told explicitly not to
  change topic until it has a *why*.
- **Clearer notes, in the studio's words.** Short sections on the clipboard:
  - **Name**
  - **Loves** (the element): "slow progress you can see"
  - **Because**: "it feels earned"
  - **Not a fan of**
  - **Wants to make**
  - **Feels ready**: 2/5
- **The tablet tests follow the talk.** They're offered when they connect to what was said ("you
  said movement matters: try these two jumps"), not in a fixed order.
- **The profile gets used.** Today the learner card is collected and never read. It should shape
  the examples characters use ("like RuneScape's skill bars"), which systems the kid's game grows
  (§7), and which department leads next.
- **The look joins the app.** The dusk-brown lobby becomes League Navy. The scene and silhouette
  stay; the palette, the bubble and the input match the studio. (This reverses DESIGN.md's "Front
  Door exception", at Jay's request.)

## 6. The UI: Impeccable critique summary (full report in chat and in `.impeccable/critique/`)

**Score: 18/40, "Poor"** (a full Unity-like shell with broken interaction details). The work, in
priority order:

1. **Every voice gets its own panel.**
   - Chat becomes a dock with **one tab per character**. A new speaker opens their own tab; old
     tabs keep an unread dot.
   - Each character has an **identity colour** on the avatar disc, bubble edge, tab icon, panel
     header and question card (decision R3). It never appears on buttons, selection or focus, so
     orange stays the call to action.
   - Each character has its own icon, in inline Lucide (decision R4).
2. **Game events are not speech.** Events become thin full-width system rows with an icon ("▶ Play
   started", "Coin grabbed, no sound", "Ticket filed"). They also go to a real **Console** tab. The
   character's reaction follows as its own bubble.
3. **The Unity layout.**
   - **Tickets** gets its own dock (left, above Hierarchy), with clickable rows and the current
     ticket expanded.
   - **Project** becomes Unity's two-column browser: folders on the left (Assets › Sprites, Sounds,
     Scripts, Docs, Cards) and a thumbnail grid on the right. It holds everything: assets, code,
     the design doc, cards.
   - **Console** sits beside Project.
   - The Hierarchy root is a **Scene** ("Level 1"), without the gloss.
4. **A Unity-faithful Inspector.**
   - An **object field** (thumbnail or icon, asset name or "None", a ◉ picker) opens a searchable
     picker with a preview. You can drag from Project into the slot, or tap an asset and then tap
     the slot.
   - Each slider has a number box. There's a colour field. Each component header has a fold, an
     enable checkbox, an icon and a name.
   - **More properties per component:**
     - Transform: Position, Scale;
     - Sprite Renderer: Sprite, Color, Flip;
     - Box Collider 2D: Is Trigger, Size;
     - Rigidbody 2D: Gravity Scale;
     - Audio Source: Clip, Volume, Pitch;
     - scripts: Speed, Jump Force.
   - Quests check only their own field; Play-mode revert makes experimenting safe.
5. **Stop over-explaining.**
   - Remove the kid glosses on tabs ("your studio's files", "the intern's game"), the Hierarchy
     notes ("the level", "looks broken", which also give the answer away), the triple "Mentor"
     label, and the hint line under every card.
   - Tooltips carry the plain words, and they work on tap as well as hover.
6. **Question card fixes:** no pre-selection; highlight only on hover or keyboard focus; no fake
   choices; the game name is typed in chat, with suggestions made from the kid's *own* hero word.
7. **Accessibility:**
   - Every line is announced twice (`role="log"` plus a separate live announcer).
   - Contrast failures: quiet ink on the selection colour (3.63:1) and on the kid's bubble (4.19:1).
   - Borders under 3:1: the input border, the range track, the splitter focus.
   - Targets under 44px: menu bar 30px, dock tabs 30px, close 32px.
8. **Art: lay off Kenney for now.** Go back to the wireframes' simple code-drawn shapes (the flat
   pixel-rect heroes in `wireframes/src/04-first-day.template.html:218`). This also dissolves the
   scale problem. *Later:* research one very large, single-style pack that can cover many genres.

## 7. The course: a whole studio year that doesn't repeat

**The problem to design against:** every shift today has the same shape (tap part → flip toggle →
Play → quiz). Ten sessions of that is a worksheet. The curriculum map (`curriculum-map.md` §6) has
the right arc, but only session 1 exists, and the built session 1 already spends concepts the map
saves for sessions 3–6 (collider, feedback, readability, risk).

**Four levers make it feel unique to each kid:**

1. **Their player profile (from the interview) seeds the game's growth.**
   - An explorer's game grows secrets and a map; a grinder's grows collecting and upgrades.
   - A story kid's grows characters who talk; a challenge kid's grows a boss; a social kid's grows
     2-player.
   - The same concepts reach every kid, through different builds.
2. **A different *verb* each session,** so the work itself changes:
   - Engineering *debugs* ("which line did that?");
   - Audio *listens and mixes*;
   - Art *directs a style*;
   - Design *tunes and playtests*;
   - QA *reproduces bugs*;
   - Production *cuts scope*;
   - Publishing *pitches and ships*.
3. **Guidance tapers on evidence, not the calendar:** *guided shifts → the kid leads (writes the
   ticket, the Builder builds, the kid checks it in the Inspector and Script) → free build*. The step
   up happens when the kid has directed N Builder changes that passed the Checker.
4. **Surprise, not routine:**
   - tool unlocks (particle maker, level painter, mixer);
   - client emails;
   - a customer ticket from last week's concept (spaced retrieval in disguise);
   - a "new intern" who asks the kid to explain something.

**Draft arc (ten sessions, ~75–90 min each):**

| # | Studio day | Verb | Owned concepts | Their game gains | Unity idea it prepares |
|---|---|---|---|---|---|
| 1 | Hired | play, find, fix one | engine, Play mode, Hierarchy | the intern's level becomes theirs; hero + name | Play mode, Scene, GameObject |
| 2 | Engineering | tune | Inspector, gravity, game loop | jump feel that fits *their* profile | Inspector, components, Update |
| 3 | Design | playtest | mechanic, core loop, win/lose | a goal and a way to lose | a game's rules |
| 4 | Audio | listen and mix | feedback, sound effect, event | sounds for every action | AudioSource, events |
| 5 | Engineering | debug | collider, bug, script, variable | the first code peek, "which line did that?" | Collider2D, scripts, variables |
| 6 | Art (**Alpha**) | direct a style | sprite, component, prefab | their look; a reusable enemy or coin | Prefabs, Sprite Renderer |
| 7 | Animation & VFX | juice | frames, particles, juice | hits that feel good | Animator, Particle System |
| 8 | All departments (**Beta**) | the Door Problem | iterate | one feature, argued by every department | the studio pipeline |
| 9 | QA + Production | reproduce and cut | (retrieval) | bug-fix patch 1.1 from friends' playtests | Console, bug reports |
| 10 | Publishing (**Launch**) | pitch and ship | (retrieval) | the credits, the Showcase wall, "teach the new intern" | Build & publish |

**Every session keeps the same frame** (`prototype-plan.md` §4), so kids know the rhythm while the
work inside changes:
1. stand-up (the kid plays their game while a character asks about last week);
2. the main shift;
3. a customer ticket;
4. studio time;
5. show a friend.

**What the engine needs for this** (the whole-V2 review, §3):
- a **component schema** shared by the Inspector, the validator, the mentor's allowed changes and
  the Builder (today part ids are hard-coded in four places);
- events declared by the game code;
- sessions and milestones;
- the Director;
- per-concept mastery (Leitner: new / learning / solid / strong);
- save migrations.

## 9. Decisions (Jay, 2026-09-28) and open questions

**Decided:**
- **R1. The AI is chat-first; code keeps the score** (option C, §4). The quest holds the goals,
  evidence and hint levels, and the AI picks the wording and order inside them.
- **R2. Heroes are shape heroes the AI builds.** They're code-drawn from parts (body, colour, eyes,
  horns, wings, tail, and so on), like the wireframes. "A dragon" is assembled as a dragon. No
  Kenney hero sprites.
- **R3. Each character has a full identity colour.** Their hue is on their avatar, bubble edge, tab
  icon, *and* their panel header and question card. This amends D15: orange stays the call to
  action and the selection colour, and character hues never go on buttons or focus rings. Each hue
  must still pass AA against the navy it sits on.
- **R4. Icons are inline Lucide.** Stroke-based, 24-grid, drawn at 1.75 to match the house set, and
  copied into the page as SVG (no dependency, no icon font).

**Still open:**
1. Should session 1 still touch all four departments, or hold them for later sessions, as the
   curriculum map's budget says (3 new terms + 1 studio word per session)?
2. Does the Builder need to be ready for Sunday (Tier 3), or is own-game time on Sunday enough with
   the wider set of settings the mentor can change?
